# 審核標準（Claude 審核每一個 PR 時檢查的項目）

Gemini 交 PR 之前可以照這份自己先檢查一次。

## 1. 範圍

- [ ] PR 只做一張工單；標題以工單編號開頭。
- [ ] 只改了工單列明的檔案（`git diff --stat` 對照工單表頭）。
- [ ] 沒有順手的重構、改名、格式化、刪除。
- [ ] PR 範本每一節都有填寫；「偏離工單的地方」和「需要 Claude 決定的問題」照實寫出。

## 2. 正確性

- [ ] 規則、數值、介面文字與總規格逐字一致。
- [ ] 工單列出的每一項測試都存在，名稱正確，而且真的在檢查工單描述的行為（不是永遠成立的斷言）。
- [ ] Claude 在本機重跑：`node tools/test.js`、`node tools/smoke.js`、`node tools/smoke-rounds.js`（存在時），全部通過。
- [ ] 改動邏輯檔案時：舊模式的模擬結果與整合分支完全相同（第十五期）。
- [ ] 邏輯檔案沒有 `Math.random`、DOM、`localStorage`；隨機數經 `R.rand`。
- [ ] 失敗的操作不會改變狀態（例如錢不夠時不會只扣錢不給東西）。
- [ ] 舊存檔可以載入（新欄位有預設值）。

## 3. 體驗（有介面改動時）

- [ ] Claude 用 Playwright 截圖：桌面 1280×800、手機 390×844。
- [ ] 手機沒有橫向捲動；按鈕夠大；文字清楚。
- [ ] 資訊量克制，沒有加回已收起的資訊。
- [ ] 演出在速度 ×4、快轉和減少動態效果時都正常。
- [ ] Claude 親手玩一次相關流程，記錄感覺和問題。

## 4. 平衡（有規則或數值改動時）

- [ ] `node tools/sim-rounds.js 200`（存在時）達到當期的驗收數字；Claude 會用另一段 seed 重跑確認穩定。

## 5. 結論

Claude 在 PR 留言，格式：

```
審核結論：通過／小修改／要重做

必須修改：
1. 檔案:行號 — 問題 — 建議的做法

建議（可選）：
- …

已驗證：
- node tools/test.js：N 項通過
- node tools/smoke.js：通過
- ……
```

- **通過**：可以合併。Claude 更新 `docs/workorders/README.md` 的狀態表；如果實作揭示規格需要調整，同時修訂之後的工單（每張工單底部有「修訂紀錄」）。
- **小修改**：在同一條分支修改，推送後 Claude 再審。
- **通過（附小修正）**：只差幾行、或者是規格沒有寫清楚的地方，Claude 在合併時直接修正並補測試，記在審核意見裡，不用再交回 Gemini。
- **要重做**：Claude 說明原因，必要時先修訂工單。
